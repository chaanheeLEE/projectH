### [ADR-001] 주문 재고 동시성 제어를 위한 낙관적 락 적용

- **관련 단계**: 1단계 3주차 주문/재고 동시성 제어 개발 중
- **상황 및 배경 (Context)**
  - 다수의 사용자가 인기 상품을 동시에 대량으로 구매할 때, 여러 트랜잭션이 한 상품의 재고 수량(`Stock`)을 변경하려고 경쟁합니다.
  - 이로 인해 발생하는 레이스 컨디션(Race Condition)과 데이터 부정합(초과 판매 등)을 제어해야 합니다.

- **비교 분석 및 대안 (Options & Trade-offs)**

  | 대안 | 장점 (Pros) | 단점 (Cons) | 비고 |
  | :--- | :--- | :--- | :--- |
  | **대안 A: 낙관적 락 (Optimistic Lock) + Spring Retry (선택)** | - DB 레벨의 물리적 락을 오랫동안 잡고 있지 않아 커넥션 대기가 줄고 처리량이 높음.<br>- 충돌이 비교적 적은 일반적인 상황에 성능 우위. | - 충돌이 빈번할 때 재시도(Retry) 오버헤드가 발생함.<br>- 재시도 로직(Retry Policy)을 별도로 관리해야 함. | **최종 채택**: DB 점유를 최소화하고 높은 TPS 확보 가능. |
  | **대안 B: 비관적 락 (Pessimistic Lock)** | - 강력한 일관성을 보장하며, 락을 먼저 획득한 트랜잭션이 확정되므로 재시도가 불필요. | - 트랜잭션 종료 시까지 DB Row에 락을 잡고 있어 전체 시스템의 동시 처리량이 저하됨.<br>- 데드락의 위험성 존재. | 미선택 |

- **최종 결정 (Decision & Rationale)**
  - 대용량 커머스 코어 시스템의 고성능 보장을 목표로 하며, 재고 충돌 상황은 선언적 재시도(`@Retryable`)를 사용하여 복구 가능하다고 판단하여 **낙관적 락(대안 A)**을 적용하였습니다.

### [ADR-002] 주문 생성 트랜잭션과 후속 작업(재고/결제) 트랜잭션 경계 분리

- **관련 단계**: 1단계 3주차 트랜잭션 경계 및 보상 트랜잭션 설계 중
- **상황 및 배경 (Context)**
  - 주문 생성 단계에서 동기식으로 재고 차감 및 외부 PG 결제 API를 호출하면, 외부 시스템 장애가 주문 시스템으로 전파되고 DB 커넥션을 붙잡고 있는 시간이 심각하게 길어집니다.
  - 이를 방지하기 위해 단일 트랜잭션을 분리하고 물리적 단계별 최종 일관성(Eventual Consistency)을 보장해야 합니다.

- **비교 분석 및 대안 (Options & Trade-offs)**

  | 대안 | 장점 (Pros) | 단점 (Cons) | 비고 |
  | :--- | :--- | :--- | :--- |
  | **대안 A: 단일 트랜잭션 (동기)** | - 트랜잭션 처리가 단순함. 예외 발생 시 DB가 자동으로 전체 롤백을 수행함. | - 결제 등의 외부 API 타임아웃 지연 시 DB 커넥션을 계속 유지하므로 병목의 주원인이 됨. | 미선택 |
  | **대안 B: Spring ApplicationEvent 기반 트랜잭션 분리 (선택)** | - 주문 저장 후 즉시 트랜잭션이 종료되어 응답속도가 대폭 상승함.<br>- 장애 격리(Fault Isolation) 및 단계별 결합도 완화. | - 상태 관리(PENDING $\rightarrow$ STOCK_DEDUCTED $\rightarrow$ APPROVED)가 추가되고 실패 시 명시적인 보상 트랜잭션을 구현해야 함. | **최종 채택**: Saga 패턴을 모사한 보상 트랜잭션 구조로 외부 장애 전파 차단. |

- **최종 결정 (Decision & Rationale)**
  - 서비스 확장성과 결제 모듈의 네트워크 대기 오버헤드를 근본적으로 차단하기 위해 **트랜잭션 분리(대안 B)**를 적용하였고, 결제 실패 시 차감되었던 재고를 롤백하고 주문을 취소하는 보상 트랜잭션을 구현하였습니다.

### [ADR-003] 트랜잭션 이벤트 비동기 실행 방식 결정

- **관련 단계**: 1단계 3주차 이벤트 리스너 실행 방식 설계 중
- **상황 및 배경 (Context)**
  - 트랜잭션을 분리한 후 이벤트를 구독하여 실행할 때, 이 리스너를 호출하는 방식을 동기식(메인 스레드 대기)으로 처리할지 비동기식(다른 백그라운드 스레드 사용)으로 처리할지 결정해야 합니다.

- **비교 분석 및 대안 (Options & Trade-offs)**

  | 대안 | 장점 (Pros) | 단점 (Cons) | 비고 |
  | :--- | :--- | :--- | :--- |
  | **대안 A: `@Async` + `@TransactionalEventListener` (선택)** | - 주문 트랜잭션이 완전히 DB 커밋 완료된 후 비동기로 수행됨.<br>- 메인 응답 속도 극대화. | - 비동기 스레드에서 예외 발생 시 호출 스레드가 이를 바로 인지하지 못하므로, 로깅 및 보상 처리가 엄격해야 함. | **최종 채택**: 응답성과 동시 처리성 극대화를 위해 선택. |
  | **대안 B: `@EventListener` (동기) + `REQUIRES_NEW`** | - 하나의 스레드에서 차례대로 예외 로그가 기록되어 디버깅 및 에러 추적이 쉬움. | - 메인 스레드가 결제 요청과 같은 외부 API 시간만큼 대기해야 하므로 성능 병목 유발. | 미선택 |

- **최종 결정 (Decision & Rationale)**
  - 대규모 트래픽 발생 시 사용자의 대기 시간을 단축하고 처리량(Throughput)을 최대로 올리기 위해 **비동기 이벤트 리스너 구조(대안 A)**를 적용하였습니다.

### 🛠️ 시행착오 및 극복 과정 (Lessons Learned)

#### 1. `@Retryable` 자가 호출(Self-invocation) 프록시 누락 문제
*   **문제**: 처음에는 `OrderEventListener` 클래스 내부의 일반 private/public 메서드에 `@Retryable`을 선언하고 이벤트를 수신한 스레드 내에서 재시도를 시도했으나, 낙관적 락 발생 시 재시도가 전혀 작동하지 않는 현상을 겪었습니다.
*   **원인**: 스프링 AOP 프록시 메커니즘 상, 동일한 빈 인스턴스 내부의 메서드 간 직접 호출(Self-invocation) 시 프록시 가로채기(Interceptor)가 작동하지 않아 AOP 기반 `@Retryable` 어노테이션이 무시된 것이었습니다.
*   **해결**: 재고 차감 및 리트라이 비즈니스를 주관하는 별도의 전용 컴포넌트인 `StockDeductionFacade` 클래스를 분리 생성하였습니다. `OrderEventListener`가 분리된 `StockDeductionFacade` 빈을 주입받아 호출하게 하여 AOP 프록시를 타게 만듦으로써 재시도가 정상 작동하게 해결했습니다.

#### 2. 엔티티-도메인 객체 분리 구조에서의 `@Version` 유실 현상
*   **문제**: `Product` 도메인 객체는 순수 자바 객체이고, `ProductJpaEntity`는 JPA 매핑용 객체입니다. DB 레벨의 낙관적 락을 유도하고자 `ProductJpaEntity`에만 `@Version`을 선언하고, 비즈니스 조작 이후 저장하는 어댑터 레이어를 구성했으나 실제 동시성 경합 시 낙관적 락 예외가 터지지 않는 문제를 발견했습니다.
*   **원인**: `ProductRepositoryAdapter.save(product)` 호출 시 도메인 객체를 기반으로 새로운 `ProductJpaEntity` 인스턴스를 매번 매핑하여 `save()` 메서드로 던지기 때문에, 기존에 DB에서 조회했을 때 획득했던 `version` 정보가 새로운 엔티티에 세팅되지 않고 `null`인 상태로 JPA에 머지(merge)되었습니다. 이에 따라 JPA는 버전 검증을 누락한 채 업데이트를 수행하게 되어 낙관적 락이 무력화되었습니다.
*   **해결**: 순수 도메인 객체인 `Product`에도 `version` 필드를 추가하고, `ProductMapper`를 통해 DB 엔티티 조회 시 도메인 객체로 `version`을 담아갔다가, 다시 영속성 레이어로 넘어갈 때 `version`을 전달하는 양방향 매핑을 완벽히 구축하여 낙관적 락이 올바르게 동작하도록 정상화했습니다.
