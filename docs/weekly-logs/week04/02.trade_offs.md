# ⚖️ [4주차] 의사결정 및 트레이드오프 (Trade-offs & ADR)

### [ADR-001] 순수 Java 객체 기반 결제 상태 머신(State Machine) 설계 및 캡슐화

- **관련 단계**: 2단계 4주차 결제 상태 머신 설계
- **상황 및 배경 (Context)**
  - 외부 PG사 결제 연동 시 네트워크 연결 지연, 사용자 결제창 이탈, 중복 승인 요청, 결제금액 위변조 등 다양한 예외 상황이 발생할 수 있습니다.
  - 이에 따라 결제 객체가 잘못된 상태로 전이되는 것을 방지하고, 각 상태에서 허용된 전이만 가능하도록 엄격한 검증 매커니즘이 필요합니다.

- **비교 분석 및 대안 (Options & Trade-offs)**

  | 대안 | 장점 (Pros) | 단점 (Cons) | 비고 |
  | :--- | :--- | :--- | :--- |
  | **대안 A: Pure Java Enum + Aggregate Root 캡슐화** | 외부 라이브러리 의존성이 없고, 단위 테스트 작성이 극도로 간결하며 도메인 캡슐화가 뛰어남 | 상태 전이 로직 및 이벤트 발생 규칙이 복잡해질 경우 엔티티 코드가 다소 늘어남 | **최종 선택** |
  | **대안 B: Spring StateMachine 프레임워크 도입** | 선언적 전이 정의 및 시각화/이벤트 리스너 바인딩 지원 | 도메인 레이어에 프레임워크 기술 침투, 과도한 보일러플레이트 및 학습곡선 증가 | 미선택 |

- **최종 결정 (Decision & Rationale)**
  - **대안 A (Pure Java Enum 캡슐화) 선택**:
    - `PaymentStatus` Enum 내에 전이 허용 매트릭스(`EnumSet<PaymentStatus>`)를 정의하고 `verifyTransitionTo()` 메서드를 통해 자기검증을 수행하도록 구현했습니다.
    - `Payment` 불변 도메인 객체 내부에서 `requestPg()`, `approve()`, `complete()`, `fail()`, `cancel()` 등의 캡슐화된 메세지 응답 메서드를 제공하여 캡슐화와 도메인 주도 설계 원칙을 준수했습니다.

- **시행착오 및 극복 과정 (Lessons Learned)**
  - `Money` VO에 금액 검증을 위한 `isLessThanOrEqualZero()` 및 static 팩토리 메서드 `wons()`가 부족하여 초기 단위 테스트 컴파일 실패가 발생했습니다.
  - 이를 해결하기 위해 `Money` 도메인 VO에 필요 연산/검증 메서드를 보완하여 rich domain model 형태로 개선하였습니다.

### [ADR-002] DB Unique Index 기반 멱등성 키(Idempotency Key) 및 PG 서버 측 위변조 검증 설계

- **관련 단계**: 2단계 4주차 중복 결제 방지 및 승인 검증
- **상황 및 배경 (Context)**
  - 동일한 결제 요청이 네트워크 재시도나 고객의 중복 클릭으로 인해 여러 번 발생할 수 있으며, 이로 인해 중복 결제가 발생하면 심각한 시스템 문제로 이어집니다.
  - 또한, 프론트엔드 결제창 호출 시 전달되는 금액을 클라이언트에서 조작(위변조)할 수 있는 보안 취약점이 존재합니다.

- **비교 분석 및 대안 (Options & Trade-offs)**

  | 대안 | 장점 (Pros) | 단점 (Cons) | 비고 |
  | :--- | :--- | :--- | :--- |
  | **대안 A: DB Unique Constraint + PortOne 단건 조회 검증** | 추가적인 분산 캐시/락 인프라 없이 RDBMS 레벨에서 확실한 중복 결제 차단 및 정확한 단건 조회 검증 | DB 유니크 제약 조건 충돌 예외 핸들링 필요 | **최종 선택** |
  | **대안 B: Redis 기반 분산 락 및 단순 클라이언트 승인** | 빠른 응답 속도 | Redis 인프라 관리 부담 증가 및 클라이언트 단독 승인 시 결제 금액 위변조 공격에 무방비 | 미선택 |

- **최종 결정 (Decision & Rationale)**
  - **대안 A 선택**:
    1. 결제 준비 단계에서 클라이언트가 생성한 `idempotencyKey` (UUID)를 결제 데이터베이스의 Unique Index로 저장하고, 동일한 멱등키로 재요청 시 이전 결제 내역을 멱등하게 반환합니다.
    2. 결제 검증 단계에서 PG사(`PortOne`) 단건 결제 조회 API를 백엔드에서 호출하여 `PG 실제 승인 금액 == 서버 DB 주문 금액`을 철저히 재검증합니다.
    3. 만약 위변조가 감지될 경우, 즉시 PG 취소 API를 호출하고 결제 상태를 `FAILED`로 전이시켜 안전성을 확보했습니다.
