# 1주차 개발 시행착오 및 트레이드오프 (Trade-off)

1주차 도메인 설계 및 모델링 단계에서 발생한 의사결정 사항들과 트레이드오프에 대해 기록합니다.

---

### 📝 [ADR-001] 장바구니(Cart)와 주문(Order) 도메인의 분리 여부

- **관련 단계**: 1단계 1주차 DDD 도메인 모델링
- **상황 및 배경 (Context)**
  - 상품 선택 및 구매 흐름에서 "장바구니에 담기"와 "주문 생성"은 밀접하게 연동되어 있습니다. 이를 하나의 Bounded Context(주문 도메인)로 묶어 관리할 것인지, 독립적인 서비스 경계로 나눌 것인지 결정해야 합니다.

- **비교 분석 및 대안 (Options & Trade-offs)**

  | 대안 | 장점 (Pros) | 단점 (Cons) | 비고 |
  | :--- | :--- | :--- | :--- |
  | **통합 (하위 엔티티)** | - 테이블 구조가 단순해짐.<br>- 장바구니에서 주문으로 이행될 때 상태 변환 코드가 편리함. | - 두 도메인의 생명주기(Life Cycle)가 다른데 강하게 결합됨.<br>- 장바구니 조회/추가 빈도가 높은 서비스 특성상 주문 DB에 부하를 줄 수 있음. | 미선택 |
  | **분리 (Bounded Context 분리)** | - 장바구니는 빈번하게 생성/변경/삭제되는 휘발성 성격이므로 격리 가능.<br>- 향후 장바구니 데이터베이스만 Redis 등으로 쉽게 전환 가능. | - 장바구니 ➔ 주문 이행 시 데이터를 복사하고 검증하는 로직이 추가로 필요함. | **선택** |

- **최종 결정 (Decision & Rationale)**
  - **분리 설계**를 선택했습니다. 장바구니는 세션이나 캐시(Redis 등) 기반의 고속 조회가 필요한 도메인인 반면, 주문은 금융 및 법적 증빙이 필요한 강한 트랜잭션이 요구되므로, 둘의 관심사와 인프라적 요구 조건이 상이합니다. 따라서 도메인을 Bounded Context 수준에서 철저히 분리하기로 결정했습니다.

### 📝 [ADR-002] 도메인 모델 설계 방식: Rich Domain Model vs Anemic Domain Model

- **관련 단계**: 1단계 1주차 도메인 엔티티/VO 모델 설계
- **상황 및 배경 (Context)**
  - 비즈니스 규칙과 상태 변경 검증 로직을 도메인 모델(Entity, VO) 내에 내재화할 것인지, 아니면 전형적인 서비스 레이어(Service) 중심의 개발 방식을 따를 것인지 결정해야 합니다.

- **비교 분석 및 대안 (Options & Trade-offs)**

  | 대안 | 장점 (Pros) | 단점 (Cons) | 비고 |
  | :--- | :--- | :--- | :--- |
  | **Anemic Domain Model**<br>(빈약한 도메인 모델) | - 구조가 단순하고 Spring/JPA 개발자들에게 매우 친숙함.<br>- 엔티티는 데이터 컨테이너 역할만 하므로 코드가 단순함. | - 비즈니스 로직이 서비스 레이어에 파편화됨.<br>- 엔티티 상태를 외부(Service)에서 강제로 바꿀 수 있어 캡슐화가 깨짐. | 미선택 |
  | **Rich Domain Model**<br>(풍부한 도메인 모델) | - 비즈니스 규칙(Invariants)이 엔티티 내에 모여있어 유지보수가 용이함.<br>- 도메인 객체가 스스로를 검증하므로 객체 지향 원칙에 부합함. | - 도메인 내 로직이 밀집되어 테스트 작성 및 적응에 초반 비용이 발생함. | **선택** |

- **최종 결정 (Decision & Rationale)**
  - **Rich Domain Model**을 선택했습니다. 본 프로젝트는 DDD 설계를 지향하고 있으며, 특히 주문 및 결제의 상태 전이(`INITIATED` ➔ `PG_REQUESTED` 등) 시에 도메인 규칙을 명확히 보장해야 합니다. 상태 전이 제어권을 도메인 모델 내부로 캡슐화하여 서비스 레이어의 복잡성을 낮추기 위해 이를 선택하였습니다.
