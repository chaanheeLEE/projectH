# ⚖️ 2주차 의사결정 및 트레이드오프 (Trade-offs)

이 문서는 2주차 개발 진행 과정에서 발생한 아키텍처 설계 결정과 기술 선택에 따른 트레이드오프 및 시행착오를 기록합니다.

---

### [ADR-001] Spring Multi-Module 구조 설계 전략 선택

- **관련 단계**: 1단계 2주차 Spring Multi-Module 구조 설계
- **상황 및 배경 (Context)**
  - 8주차에 예정된 Kafka 기반 MSA 전환 및 비동기 분할을 원활히 지원하고, 각 레이어(계층) 간의 결합도를 낮추는 강력한 구조적 제한 장치가 필요했습니다.
  - 이를 위해 도메인을 패키지로 나눌 것인가, Gradle 모듈 단위로 나눌 것인가에 대한 아키텍처 결정이 요구되었습니다.

- **비교 분석 및 대안 (Options & Trade-offs)**

  | 대안 | 장점 (Pros) | 단점 (Cons) | 비고 |
  | :--- | :--- | :--- | :--- |
  | **대안 A** (레이어 중심 멀티 모듈) | - 초기 빌드 오버헤드가 낮고 구조가 상대적으로 직관적임.<br>- 단일 애플리케이션 트랜잭션 관리가 용이함.<br>- 순수 도메인 모듈(domain)의 격리가 용이함. | - 8주차 MSA 분리 단계에서 도메인 간의 코드 커플링이 있을 경우, 서비스별 물리적 이관 작업이 까다로울 수 있음. | **최종 선택** (패키지 기준의 엄격한 도메인 격리를 병행하여 한계 보완) |
  | **대안 B** (도메인 중심 멀티 모듈) | - 도메인 간 물리적인 차단이 Gradle 의존성을 통해 강제되어 아키텍처 정합성이 완벽히 유지됨. | - 모듈 개수가 과도하게 증가하여 빌드가 느려짐.<br>- 모듈 간 협업 시 순환 참조 가능성이 높아짐. | 미선택 |

- **최종 결정 (Decision & Rationale)**
  - **대안 A (레이어 중심 멀티 모듈)**을 채택하였습니다. 
  - 학습 곡선과 프로젝트 초기 진행 속도를 고려하고, `domain`, `application`, `infrastructure`, `api` 모듈 내에서 `product`, `cart` 등 도메인 패키지 단위를 아주 명확하게 분할하여 차후 MSA 전환 시점에 도메인 패키지 자체를 독립 모듈로 들어내기 편하게 격리했습니다.

### [ADR-002] JPA Entity ↔ Domain 객체 분리 원칙 적용

- **관련 단계**: 1단계 2주차 JPA 매핑 시 Entity ↔ Domain 객체 분리
- **상황 및 배경 (Context)**
  - JPA Entity는 데이터베이스 테이블 구조와 1:1 매핑되어 데이터베이스 물리 모델에 강하게 의존합니다.
  - 핵심 비즈니스 로직(예: 재고 차감 시 품절 상태 전이 규칙)이 JPA 기술 프레임워크나 테이블의 스키마 변경에 종속되지 않도록 자바 POJO 도메인 모델을 완벽히 격리해야 했습니다.

- **비교 분석 및 대안 (Options & Trade-offs)**

  | 대안 | 장점 (Pros) | 단점 (Cons) | 비고 |
  | :--- | :--- | :--- | :--- |
  | **대안 A** (도메인 모델과 JPA Entity의 엄격한 분리) | - 도메인 모델이 JPA 프레임워크에 오염되지 않고 순수한 비즈니스만 담음.<br>- 데이터 스토어를 RDBMS에서 NoSQL로 바꾸더라도 도메인은 완전히 안전함. | - Entity ↔ Domain 객체 간의 Mapper 보일러플레이트 코드가 증가함.<br>- JPA의 변경 감지(Dirty Checking) 및 지연 로딩(Lazy Loading) 혜택을 100% 누리지 못해 저장 시 추가 처리가 필요함. | **최종 선택** (학습 가이드 준수 및 클린 아키텍처 정합성 확보) |
  | **대안 B** (JPA Entity 자체를 도메인 모델로 혼용) | - Mapper 변환 비용이 없고 Dirty Checking을 활용하여 개발 생산성이 높음. | - 도메인 로직에 JPA 애노테이션(@Id, @Column 등) 및 ORM 관련 로직이 섞여 설계적 순수성이 저하됨. | 미선택 |

- **최종 결정 (Decision & Rationale)**
  - **대안 A (엄격한 분리)**를 최종 채택하였습니다. 
  - 도메인 중심의 비즈니스 코드를 보존하고, `projecth-domain`이 Spring/JPA 라이브러리 없이 독립적으로 완벽하게 빌드 및 테스트될 수 있게 만들기 위함입니다.
  - Mapper로 인한 수동 매핑 작업이 수반되지만, 비즈니스 규칙이 안전하게 검증된다는 점이 더 가치있다고 판단했습니다.

- **시행착오 및 극복 과정 (Lessons Learned)**
  - **문제점**: 도메인 객체를 JPA Entity로 수동 매핑하여 매번 `save`를 호출할 때, `Cart` (Aggregate Root) 내부의 `CartItem`들을 단순 덮어쓰기 방식으로 저장하면 영속성 컨텍스트 상에서 새로운 `CartItemJpaEntity`들이 영속화되어 `Duplicate Key` 에러나 혹은 `Orphan Removal`이 오동작하는 문제가 발생했습니다.
  - **해결 방안**: `CartRepositoryAdapter`에서 영속성 컨텍스트에 기존 장바구니 엔티티가 이미 존재하는지 미리 조회하고, 존재한다면 기존 엔티티를 활용하여 자식 리스트만 변경(`updateItems`)해주어 JPA의 변경 감지 메커니즘을 복원함으로써 해당 영속성 정합성 문제를 해결하였습니다.
