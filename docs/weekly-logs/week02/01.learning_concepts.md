# 📚 [2주차] 필수 이론 학습 및 개념 정리 노트

이 문서는 1단계 2주차 개발을 진행하기 위해 학습한 DDD 핵심 이론, Spring Multi-Module 아키텍처 규칙, 그리고 Entity-도메인 격리에 따른 트레이드오프 분석을 정리한 노트입니다.

## 1. 🧩 Domain-Driven Design (DDD) 핵심 개념

### ① Entity(엔티티) vs Value Object(VO, 값 객체)
- **Entity**:
  - **정의**: 식별자(Identifier)를 가지고 있어 시스템 내에서 유일하게 구분되는 객체입니다.
  - **특징**: 객체의 속성값이 변하더라도 식별자가 동일하면 같은 객체로 취급하며, 생명주기(Lifecycle)를 가집니다. (예: `Product` - 가격과 재고가 바뀌어도 ID가 동일하면 같은 상품임)
- **Value Object (VO)**:
  - **정의**: 고유한 식별자 없이 단순히 '속성값들의 조합'으로만 정의되는 객체입니다.
  - **특징**: 값이 같으면 동일한 것으로 판단(동등성, `equals` 오버라이딩 필수)하며, 사이드 이펙트를 방지하기 위해 반드시 **불변성(Immutability)**을 유지해야 합니다. 값을 변경하려면 새로운 VO를 생성해 교체해야 합니다. (예: `Money`, `Stock` - 5000원이라는 값 자체는 고유 ID를 가질 필요가 없음)

### ② Aggregate(애그리거트)와 Aggregate Root(애그리거트 루트)
- **Aggregate**:
  - **정의**: 밀접하게 연관된 도메인 객체들(Entities, VOs)을 하나의 정합성 경계로 묶은 데이터 군집입니다.
- **Aggregate Root**:
  - **정의**: 애그리거트 내부 객체들에 직접 접근하는 것을 제어하고, 애그리거트 전체의 일관성 및 비즈니스 제약 규칙을 유지하는 관문(Gateway) 역할을 하는 유일한 대표 엔티티입니다.
  - **트랜잭션 경계 설정 기준**:
    - **1 트랜잭션 = 1 애그리거트 수정**: 하나의 트랜잭션에서는 원칙적으로 하나의 애그리거트 상태만 수정해야 합니다. 이를 통해 데이터 결합도를 낮추고 동시성 충돌을 예방합니다.
    - 외부 객체는 오직 애그리거트 루트의 ID를 통해서만 애그리거트 내부를 참조해야 하며, 내부 객체(예: `CartItem`)를 직접 수정할 수 없고 반드시 루트(`Cart`)의 비즈니스 메서드를 통해서만 제어해야 합니다.

### ③ Domain Service(도메인 서비스) vs Application Service(응용 서비스)
- **Domain Service**:
  - **개념**: 단일 엔티티나 애그리거트의 책임으로 할당하기 어색한 복수의 도메인 모델 간의 협력 비즈니스 로직을 처리하는 무상태(Stateless) 서비스입니다.
  - **핵심**: 순수한 비즈니스 규칙만 포함하며, 기술적인 인프라(DB 저장, 트랜잭션 처리 등)에 절대 관여하지 않습니다.
- **Application Service**:
  - **개념**: 비즈니스 유스케이스의 흐름 제어, 데이터베이스 트랜잭션 경계 설정, 보안 권한 검증, 인프라 계층(Port) 호출 등을 담당하는 오케스트레이터입니다.
  - **핵심**: 비즈니스 판정 로직을 포함하지 않고 오직 도메인 모델에게 명령을 전달하는 조율자 역할만 담당합니다.

## 2. 📂 Spring Multi-Module 아키텍처 설계

### ① 계층 간 의존성 방향 설계 (의존성 역전 원칙 - DIP)
멀티 모듈 구조에서는 하위 모듈이 상위 기술 모듈에 종속되지 않도록 통제해야 합니다.
- **의존성 방향**: `api` ➔ `infrastructure` ➔ `application` ➔ `domain`
- **의존성 역전(DIP) 적용**:
  - `application` 레이어는 DB 영속화가 필요하지만, 인프라의 JPA에 의존하지 않기 위해 내부에 포트 인터페이스(`ProductRepositoryPort`)를 정의합니다.
  - `infrastructure` 레이어에서 이 포트 인터페이스를 상속받아 실제 JPA 기술로 구현(`ProductRepositoryAdapter`)합니다.
  - 이를 통해 비즈니스 핵심 코드가 특정 데이터베이스 기술이나 인프라 환경의 변경에 흔들리지 않는 독립성을 확보합니다.

## 3. ⚖️ JPA Entity ↔ Domain 객체 분리 및 매핑 비용 분석

도메인 모델의 순수성을 지키기 위해 JPA Entity와 순수 자바 객체(Domain)를 물리적으로 격리하여 사용함에 따른 비용과 이점을 비교 분석했습니다.

### ① 격리 설계에 따른 매핑 오버헤드와 이점

| 항목 | JPA Entity와 도메인 모델 일치 (실용) | JPA Entity와 도메인 모델 엄격 격리 (이상) |
| :--- | :--- | :--- |
| **도메인의 순수성** | 낮음 (JPA 애노테이션, 연관관계 매핑 및 DB 스키마 종속성 침투) | 매우 높음 (순수 자바 코드 및 비즈니스 로직에만 100% 집중) |
| **개발 생산성** | 높음 (Dirty Checking, Lazy Loading, JPA 기능 직접 활용) | 보통 (매 요청/저장마다 Mapper를 통한 인스턴스 복사 및 매핑 필요) |
| **테스트 용이성** | 보통 (테스트를 위해 Spring Data JPA / H2 환경 필요) | 매우 높음 (도메인 단독으로 가벼운 순수 JUnit 단위 테스트 가능) |
| **구조적 복잡성** | 낮음 | 높음 (Entity, Domain 객체, Repository, Adapter, Mapper 클래스 개수 증가) |

### ② 격리 설계 시 발생하는 매핑 비용 및 해결책
1. **메모리 및 객체 복사 비용**:
   - 매번 DB 조회 시 `JpaEntity` 생성 후 `Domain` 객체로 변환하고, 저장 시 다시 `JpaEntity`로 변환하여 저장하게 됩니다.
   - **해결책**: 매핑 비용이 발생하지만, 일반적인 커머스 환경의 단순 CRUD 조회는 추후 CQRS 패턴을 적용하여 조회 전용 DTO로 직접 꽂아 변환 오버헤드를 우회할 수 있습니다.
2. **JPA 변경 감지(Dirty Checking) 무력화**:
   - 순수 자바 객체에서 일어난 상태 변경을 JPA가 트래킹할 수 없어 직접 `save` 어댑터를 실행해야 합니다.
   - **해결책**: 어댑터 내에서 이미 존재하는 Entity일 경우 기존 객체를 영속성 컨텍스트에서 식별하여 조회한 후 내부 상태 값만 업데이트(병합 방식)하여 JPA의 변경 감지 및 Cascade Orphan Removal 혜택을 부분적으로 유지할 수 있도록 구현합니다.
